# What in useMultiUnitBookingStore is server state, what is live, and what is dead?

Research for issue #401 (map #400, Candidate 6: stores keep only UI state). Checked against `main` at `33d5fb0d` on 2026-11-10.

Method: for every field and action in `MultiUnitBookingState` / `MultiUnitBookingActions` (`src/types/multi-unit-booking.ts:177-285`), `grep -rlw <name> src` over `.ts`/`.tsx`, excluding tests, `.phase3-4` files, the store and the type file, then read each hit to drop same-name members of other stores or props. "Live" means a production component or hook calls or reads it. "Write-only" means production code writes it but nothing reads the result.

## Who uses the store in production

Only three files import it:

- `src/components/bookings/MultiUnitBookingForm.tsx:87-96` (the staff form at `/admin/bookings/new-multi`, mounted by `src/routes/admin/bookings/new-multi.tsx:34`) destructures `selectedUnits`, `addUnit`, `removeUnit`, `assignGuestsToUnit`, `getTotalAmount`, `setDraftBooking`, `recalculateTotalPricing`, `clearDraftBooking`.
- `src/hooks/useAvailabilityRealtime.ts:61` reads `selectedUnits` and `clearAvailabilityCache`.
- `src/hooks/useMultiUnitBookingQueries.ts:94` reads `addOptimisticBooking`, `removeOptimisticBooking`, `isOnline`.

Note: `src/stores/README.md:18` calls it "the guest booking form state". It is the staff form; the guest form (`MultiUnitGuestBookingForm`) does not use this store.

## How the inline pricing uses the caches (left for Candidate 3)

Pricing writes `unitPricingCache` on every recalculation and never reads it; the numbers it uses live on `selectedUnits[i].pricing`. Pricing reads `draftBooking` / `selectedBooking` only for `check_in`/`check_out` when no dates are passed, and for `discount_amount`; the form always passes the dates (`MultiUnitBookingForm.tsx:221-222,228,444`). Deleting `unitPricingCache` and `selectedBooking` therefore does not change any total, but it touches the six copies of the inline loop (`:113-120,155-167,206-218,307-319,358-370,405-417`), which Candidate 3 will replace.

## Online status: what the guard does today

`useCreateMultiUnitBooking` throws `OfflineBookingError` when the store says offline (`useMultiUnitBookingQueries.ts:98`), added in `08a95169` so offline bookings fail instead of being queued and lost. Mutations run with `networkMode: "online"` (`src/lib/query-client.ts:59`). In TanStack Query 5.104 a mutation does not start while `onlineManager.isOnline()` is false (`query-core/build/modern/retryer.js:19-20,92`): it pauses before `mutationFn`. Both the store and `onlineManager` listen to the same window events, so after an `offline` event the mutation pauses and the guard never runs. The guard fires only when the page loaded offline: the store starts from `navigator.onLine` (`:72`), but `onlineManager` starts as online (`onlineManager.js:13`). (Read from source, not run.)

So the replacement is not "read `onlineManager` instead": that would keep the pause and lose the load-offline case. Smallest correct swap: give this one mutation `networkMode: "always"` and check `navigator.onLine` in `mutationFn`. Then offline always fails fast with the existing message, and the store drops `isOnline`, `setOnlineStatus` and the listeners.

## What stays after the server state leaves

`selectedUnits`, `addUnit`, `removeUnit`, `assignGuestsToUnit`, `clearDraftBooking`, plus the Candidate 3 pricing (`calculateUnitPricing`, `recalculateTotalPricing`, `getTotalAmount`) and possibly `draftBooking`/`setDraftBooking`. That is a small form-state store for one page; there is nothing left to split.

## Decisions for the slice-order ticket (#403)

1. Delete all dead availability code (`availabilityCache`, the three check actions, `clearAvailabilityCache` and its call in `useAvailabilityRealtime`) in one slice, along with `db.bookings.checkMultiUnitAvailability` (`src/lib/supabase.ts:239`, no caller). **Default: yes, first slice; no new query needed, `useMultiUnitAvailability` already covers it.**
2. Optimistic create: drop `onMutate`/`onError`/`onSuccess` and the store's `bookings`/`optimisticQueue`/conflict code and the `setInterval`, or move to `setQueryData` on a list key. **Default: drop; nothing on screen shows the temp booking.**
3. Online guard: `networkMode: "always"` + `navigator.onLine` in `mutationFn`, or `onlineManager.isOnline()`. **Default: `navigator.onLine` with `networkMode: "always"`, because `onlineManager` pauses instead of failing and misses a page loaded offline.**
4. `draftBooking`: keep it persisted, keep it in memory only, or delete it. It is written at submit and never restored, and it can leave guest PII in `localStorage`. **Default: delete `draftBooking`, `setDraftBooking` and the `persist` middleware; pass dates and discount to pricing explicitly when Candidate 3 lands. Until then, at least stop persisting it.**
5. Dead UI members (`updateUnit`, `reorderUnits`, `selectUnit`, `applyBulkDiscount`, `clearDiscount`, `getTotalGuests`, `getUnitCount`, `canAddMoreUnits`, `hasUnavailableUnits`, `getUnavailableUnits`, `saveDraftBooking`, `loadDraftBooking`, `setLoading`, `setError`, `isLoading`, `error`, `selectedBooking`, `unitPricingCache`): delete in this effort or leave for Candidate 3. **Default: delete the non-pricing ones here; leave `applyBulkDiscount`/`clearDiscount`/`unitPricingCache` to Candidate 3 since they sit inside the pricing loops.**
6. Split the store. **Default: no; what remains is one page's form state.** Fix the stale `src/stores/README.md:18` line ("guest booking form") in the same PR.
