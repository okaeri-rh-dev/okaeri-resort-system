Research for issue #343 (map #262). Checked against `main` at `2c3d944a` on 2026-11-06. Plan under test: `docs/plans/2026-10-14-invalidate-by-domain-fact.md`, Task 1 (the "Deleted" list under Interfaces, line 70) and Task 6 (line 607). Plan baseline commit: `1b06d1b`.

Method: `grep -rnE '<factory>.<member>([^A-Za-z0-9_]|$)' src` per member, excluding `src/lib/query-keys.ts`; tests and `.md` files counted separately. Raw key roots (`"unit-availability"`, `"upcoming-checkins"`, ...) were also grepped to catch readers that bypass the factories; none were found.

"Read" means a `queryKey:` in a `useQuery`/`queryOptions`, or `setQueryData`/`getQueryData`. "Invalidated only" means the key appears only in `invalidateQueries`/`cancelQueries`, which is what the plan calls dead.

What the realtime hook actually does today:

- `useMultiUnitRealtime.ts:100-124` subscribes to two tables and invalidates `availabilityKeys.multiUnit.all` on any change. That key is read by `useMultiUnitAvailability` (`useMultiUnitBookingQueries.ts:41`), so the invalidation is live.
- Table `multi_unit_bookings` does not exist: no migration creates it and `src/types/database.generated.ts` has no such table. That half of the subscription never fires.
- Table `availability_blackouts` was added to the `supabase_realtime` publication in `supabase/migrations/20261027000000_blocks_hold.sql:360-369`, with the comment "The realtime hooks already subscribe to this table." So block writes on another device now reach the multi-unit form, refetch its availability, and show a toast (`useAvailabilityRealtime.ts:64-74`).
- `clearAvailabilityCache` (`useAvailabilityRealtime.ts:66`) clears the store's `availabilityCache`, which only `checkUnitAvailability`/`checkMultiUnitAvailability` read (`stores/useMultiUnitBookingStore.ts:437,491`), and nothing in production calls those. That part is dead.

So the plan's claim (Task 6, deleting realtime as dead) no longer holds in full: the blocks work gave it one live path (a block written on another device while the multi-unit form is open).

## Decisions this raises (for #344)

1. **`availabilityKeys.calendar` and `.blackouts` are now live.** Task 1's "Deleted" list must shrink to `calendar.byUnit`, `blackouts.byUnit` and `blackouts.range`. Recommended: edit the list that way.
2. **Task 1 Step 2's reduced `invalidateAvailability`** keeps only `availableUnits.all` and `multiUnit.all`. Today's version also invalidates `calendar.all` (the Availability timeline) and `unitKeys.allStates()` (cabin state tonight, fixed in `7cebbfd8`). Following the plan literally would break both refreshes. Recommended: keep those two in the helper, and in the `afterWrite` table map from Task 2 onward.
3. **The `afterWrite` table map has to cover blocks.** `blackouts.*` is invalidated only by `useBlocks.ts:104`, so a booking write does not refresh `blackouts.conflicts`. Recommended: decide in #344 whether the `bookings` and `availability_blackouts` tables refresh `blackouts.all`. The default is yes for `availability_blackouts`; for `bookings` it is open.
4. **Realtime on `/admin/bookings/new-multi` is not dead.** It now carries cross-device block changes, and migration `20261027000000` put `availability_blackouts` in the realtime publication for it. Options: (a) delete it as planned and accept that the form only sees another device's block on refetch or submit, since the server still rejects conflicts; (b) keep a trimmed hook that subscribes only to `availability_blackouts`. Recommended: (a), because the server is the conflict guard. If (a), also decide whether to drop the table from the publication in a migration (default: leave it; it costs nothing while nothing subscribes).
5. **Extra dead members not on the plan's list** (`upcomingKeys.*.within` goes with `upcomingKeys`; `roleKeys.detail`, `auditKeys.detail/.recent/.userActivity`). Recommended: delete the `query-keys.ts` ones in Task 1, and leave the moved local factories verbatim, since the plan says "verbatim".
6. **The line reference is stale.** The `multiUnitBookingKeys.all` cancel is now at `useMultiUnitBookingQueries.ts:103`, not `:96`. Recommended: fix the plan's line references when it is next edited. Lower priority.
